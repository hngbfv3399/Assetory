# Assetory 디자인 규칙

최종 갱신: 2026-08-04  
적용 범위: `frontend/`의 공개 안내 페이지, 상품 탐색, 상품 상세, 인증 및 이후 판매자·구매자 화면

## 1. 문서의 목적과 우선순위

Assetory는 개인 창작자가 디지털 상품을 올리고 판매하며, 구매자는 필요한 작업 시간을 줄여 주는 에셋을 발견·구매·다시 이용하는 플랫폼이다. 화면은 단순히 “예쁜 마켓”보다 다음 감각을 전달해야 한다.

- 창작물은 가볍게 소비되는 파일이 아니라, 누군가의 시간을 절약하는 작업물이다.
- 판매·구매·정산 흐름은 친절하고 투명하게 이해되어야 한다.
- 기능이 많아져도 창작자의 작업 자체가 가장 먼저 보여야 한다.

디자인 판단이 충돌할 경우 아래 순서로 결정한다.

1. 실제 사용자 흐름과 정보의 명확성
2. 접근성·반응형 안정성·성능
3. Assetory의 브랜드 톤과 페이지 간 일관성
4. 시각적 장식과 실험적 효과

즉, 장식 때문에 제목·가격·상태·다음 행동이 늦게 읽히거나 모바일에서 겹치면 장식을 제거하거나 약화한다.

### 1.1 역할별 화면의 기본 태도

| 화면 | 사용자의 목표 | 화면이 우선 보여야 하는 것 | 피해야 하는 것 |
| --- | --- | --- | --- |
| 홈·주요 기능·가격 정책 | 서비스의 가치와 다음 행동 이해 | 한 문장 가치 제안, 흐름, 명확한 CTA | 상품 정보·버튼·카피의 과밀 |
| 상품 탐색 | 필요한 에셋 발견 | 검색, 필터, 상품 비교 정보 | 과도한 장식, 필터 상태의 모호함 |
| 상품 상세 | 구매 판단 | 미리보기, 가격, 판매자, 후기, 구매 행동 | 구매 버튼이 정보 사이에 묻히는 구성 |
| 판매자 화면 | 등록·운영·의사결정 | 현재 상태, 다음 할 일, 매출/주문 변화 | 지표만 많고 행동이 없는 대시보드 |
| 구매자 보관함 | 구매 자료 재이용 | 접근 가능한 자료, 다운로드/이용 상태 | 구매 이력과 이용 가능 여부의 혼동 |

## 2. 브랜드 언어

### 2.1 핵심 인상

- **따뜻한 실용성**: 차가운 SaaS 대시보드보다 작업물과 사람의 맥락이 느껴져야 한다.
- **편집적 명료함**: 큰 제목, 분명한 경계, 넉넉한 여백으로 핵심을 먼저 읽게 한다.
- **신뢰 가능한 투명성**: 가격, Mock 결제, 예상 정산, 접근 권한의 상태를 감추지 않는다.
- **절제된 유희**: 종이, 파일, 차트, 화살표 등의 오브제는 의미를 설명할 때만 사용한다.

### 2.2 문체 규칙

- 문장은 짧고 능동적으로 쓴다. “~할 수 있게”, “~을 확인하세요”처럼 사용자가 얻는 결과를 먼저 말한다.
- 홈·기능 소개는 따뜻한 존댓말을 사용한다. 운영 화면의 상태·버튼은 간결한 명사/동사로 쓴다.
- 버튼은 동작을 명확히 쓴다. `상품 둘러보기`, `상품 등록하기`, `다운로드하기`를 우선하며, `확인`, `진행`처럼 의미가 넓은 표현은 피한다.
- 시스템 한계는 숨기지 않는다. 이 프로젝트에서 결제는 `Mock 결제`, 정산은 `예상 정산`임을 관련 화면에서 정확하게 표기한다.
- 긴 문장에 임의의 `<br />`를 넣어 모바일 줄바꿈을 강제하지 않는다. 정말 필요한 브랜드 카피만 데스크톱/모바일 규칙을 함께 설계한다.

## 3. 토큰과 시각 언어

토큰은 새 UI의 출발점이다. 현재 CSS의 실제 사용 색을 기준으로 정리했으며, 새 색을 임의로 추가하기 전에 아래 역할로 충분한지 먼저 판단한다.

### 3.1 색상

| 역할 | 값 | 사용 기준 |
| --- | --- | --- |
| 잉크/브랜드 다크 | `#17251e`, `#171b19` | 다크 헤더, 진한 CTA, 강한 구획, 중요한 숫자 |
| 브랜드 그린 | `#1f4737` | 보조 CTA, 활성 상태, 수익·신뢰 관련 강조 |
| 민트 강조 | `#c7e4cf` | 다크 영역 위의 CTA, 긍정 상태, 핵심 수수료 강조 |
| 아이보리 바탕 | `#fbf8ef`, `#f8f7f2` | 읽기 중심 본문, 카드, 밝은 표면 |
| 중성 본문 | `#56645a`, `#627282` | 보조 설명, 메타 정보 |
| 블루 섹션 | `#d6e5ff` | 가격·비교처럼 냉정한 정보를 설명하는 구획 |
| 민트 섹션 | `#c8e9e4` | 신뢰·안내·정산 원칙 구획 |
| 옐로 섹션 | `#f8dc92` | 숫자·가격처럼 즉시 주목해야 하는 구획 |
| 위험 | 명확한 대비의 red 계열 | 취소, 삭제, 접근 회수, 오류에만 사용 |

색상 사용 원칙:

- 한 화면의 **주 배경색은 하나**로 제한한다. 서로 다른 배경색은 섹션 전환의 의미가 있을 때만 사용한다.
- 다크 배경에는 아이보리 본문과 민트 강조를 사용한다. 그린 텍스트를 다크 배경에 직접 올려 대비를 낮추지 않는다.
- 의미 없는 그라데이션, 무분별한 그림자, 카드마다 다른 강조색을 사용하지 않는다.
- 성공·오류는 색만으로 전달하지 않는다. 아이콘, 상태 단어, 설명을 함께 둔다.

### 3.2 테두리와 그림자

Assetory는 두 가지 표면 언어를 구분해 쓴다.

1. **편집형(기본)**: 1~1.5px의 선명한 테두리, 낮거나 없는 그림자, 사각 또는 작은 반경. 기능 소개·가격 정책·데이터 비교에 사용한다.
2. **소프트 UI(보조)**: 밝은 중립 배경과 얕은 양각/음각 그림자. 필터, 입력 필드, 작은 조작 요소에만 제한적으로 사용한다.

- 한 컨테이너에 두 표현을 섞지 않는다. 예를 들어 굵은 검정 테두리 카드에 뉴모피즘 그림자를 중첩하지 않는다.
- 그림자는 위계를 만들 때만 사용한다. `hover` 상태에서 2~4px 정도의 작은 이동은 가능하지만, 중요한 정보가 떠 보이게 과장하지 않는다.
- 구분선은 `rgba(23, 37, 30, .24~.4)` 범위의 낮은 대비를 기본으로 하고, 페이지 챕터 전환에는 `#17251e` 1~1.5px을 사용한다.

### 3.3 모서리

- 편집형 대형 섹션·비교 표: `0` 또는 `0.5rem` 이하
- 카드·입력 컨트롤: `0.75rem`~`1rem`
- 칩·태그·작은 상태 배지: `999px`
- 한 화면의 큰 카드와 작은 버튼이 서로 다른 반경 체계를 쓰지 않도록 한다.

## 4. 타이포그래피와 한글 조판

기본 글꼴은 `Pretendard`, `SUIT`, `Noto Sans KR`, `sans-serif` 순서다. 새 글꼴을 추가하지 않는다.

### 4.1 권장 크기와 줄높이

| 용도 | 데스크톱 | 모바일 | 굵기 | 줄높이 |
| --- | --- | --- | --- | --- |
| 브랜드/히어로 제목 | `clamp(3.25rem, 5.2vw, 5rem)` 이상 | `clamp(2.35rem, 10vw, 3rem)` | 900~950 | 0.92~1.12 |
| 섹션 제목 | 2.4~3.7rem | 2.0~2.8rem | 900~950 | 1.04~1.15 |
| 카드 제목 | 1.7~2.7rem | 2.0~2.6rem (정보 카드 기준) | 850~950 | 1.05~1.2 |
| 본문 설명 | 0.95~1rem | 0.9~0.95rem | 450~650 | 1.6~1.75 |
| 메타·라벨 | 0.66~0.8rem | 0.64~0.8rem | 750~900 | 1.35~1.5 |

### 4.2 한글 줄바꿈 원칙

- 제목과 중요 설명에 `word-break: keep-all`을 적용한다.
- 제목에는 `text-wrap: balance`를 사용할 수 있지만, 두 줄 이상을 반드시 보장하는 장식 용도로 남용하지 않는다.
- 모바일에서 `br`을 숨길 경우, 앞뒤 텍스트 사이의 공백이 사라지지 않는지 반드시 확인한다. JSX에서는 `<br />{' '}다음 문장`처럼 명시한다.
- 보조 설명은 한 줄을 지나치게 길게 고정하지 않는다. 모바일에서는 자연 줄바꿈을 허용한다.
- 한국어 단어를 한 글자씩 끊어 보이게 하는 `word-break: break-all`은 URL·긴 영문 식별자 외에는 사용하지 않는다.
- 모든 대문자 영문 라벨은 0.12~0.2em 정도의 자간을 사용하되, 모바일에서는 0.18em을 넘기지 않는다.

### 4.3 숫자·금액·상태

- 가격: `12,000원`처럼 천 단위 구분을 사용한다.
- 정산: 실제 지급으로 오해되지 않도록 `예상 정산금`, `예상 금액`이라고 쓴다.
- 수수료: `단 10%`처럼 핵심 수치를 큰 크기와 높은 대비로 표현하되, 비교 근거와 설명을 바로 인접해 둔다.
- `판매 중`, `초안`, `판매 중지`, `다운로드 가능` 등의 상태는 색상·배지·텍스트를 함께 쓴다.

## 5. 레이아웃과 여백

### 5.1 컨테이너

- 일반 콘텐츠 최대 폭: `1200px`~`1240px`
- 긴 편집형 랜딩 섹션: 화면 전체 배경 위에 `1480px` 수준까지 확장 가능
- 데스크톱 좌우 여백: `max(2rem, calc((100vw - 콘텐츠폭) / 2))`
- 모바일 좌우 여백: 기본 `1.25rem`, 좁은 보조 구획은 최소 `1rem`
- 콘텐츠 영역은 항상 `min-width: 0`을 고려한다. CSS Grid의 자식에 긴 텍스트·이미지가 있으면 `minmax(0, 1fr)`을 사용한다.

### 5.2 간격 스케일

새 여백은 다음 4px 기반 단위를 우선 사용한다.

| 토큰적 의미 | 권장 값 | 사용 예 |
| --- | --- | --- |
| 아주 좁음 | 4~8px | 아이콘과 라벨, 칩 내부 |
| 좁음 | 12~16px | 폼 필드, 카드 안의 인접 요소 |
| 보통 | 20~32px | 카드 내부 블록, 버튼 묶음 |
| 넓음 | 48~72px | 섹션 제목과 콘텐츠 |
| 매우 넓음 | 96~144px | 데스크톱 챕터 전환 |

- 같은 정보 덩어리 안의 간격보다, 서로 다른 덩어리 사이의 간격이 더 커야 한다.
- 빈 공간은 장식이 아니라 읽는 순서를 만드는 수단이다. 단, 모바일에서 대형 데스크톱 여백을 그대로 유지해 콘텐츠가 첫 화면 아래로 밀리지 않게 한다.

### 5.3 섹션 구성

소개·기능 페이지는 아래 순서를 기본으로 한다.

1. 짧은 영문/한글 eyebrow
2. 한 문장 제목
3. 1~2문장 보조 설명
4. 주된 시각 요소 또는 데이터
5. 다음 행동(필요한 경우)

- 한 섹션에는 **핵심 메시지 하나**만 둔다.
- 데스크톱에서 좌/우로 정보를 배치했다면, 다음 챕터에서 시각적 순서를 반전할 수 있다. 단 모바일에서는 항상 `시각 요소 → 텍스트` 또는 `텍스트 → 시각 요소` 중 한 규칙으로 일관되게 쌓는다.
- 풀스크린 섹션은 `min-height`만 사용하고 고정 `height`는 피한다. 글자가 커져도 콘텐츠가 잘리면 안 된다.

## 6. 공통 컴포넌트 규칙

### 6.1 헤더와 푸터

- 전 페이지 헤더는 `RootLayout`의 공통 헤더를 사용한다. 새 페이지에서 별도 헤더를 만들지 않는다.
- 현재 브랜드 헤더는 다크 톤을 기본으로 한다. 밝은 본문 위에서도 헤더 자체의 색을 페이지마다 바꾸지 않는다.
- 모바일 헤더는 로고, 가장 중요한 탐색 행동, 로그인만 남긴다. 메뉴를 모두 축소해 겹치게 만들지 않는다.
- 공통 푸터는 `src/common/ui/SiteFooter.jsx`를 사용한다. 페이지 마지막의 여백을 푸터처럼 남기지 않는다.

### 6.2 버튼과 링크

| 종류 | 용도 | 형태 |
| --- | --- | --- |
| Primary | 한 섹션의 가장 중요한 행동 | 다크 또는 민트 채움, 높은 대비 |
| Secondary | 보조 행동 | 테두리, 투명 또는 밝은 표면 |
| Text link | 목록 이동·추가 정보 | 밑줄 또는 화살표를 포함한 텍스트 |
| Danger | 삭제·접근 회수 등 되돌리기 어려운 행동 | 위험색, 확인 단계 포함 |

- 동일한 시야에 Primary CTA는 하나를 원칙으로 한다.
- 버튼은 기본 40px 이상, 모바일 터치 표적은 최소 44px 높이를 확보한다.
- 버튼 라벨이 길어질 수 있는 모바일에서는 `display: flex`, `justify-content: space-between`, 적절한 `gap`을 사용하고 가로 넘침을 확인한다.
- 링크처럼 보이는 요소를 버튼으로, 버튼처럼 보이는 요소를 링크로 구현하지 않는다. 페이지 이동은 `Link`, 상태 변경·제출은 `button`을 사용한다.

### 6.3 카드

- 카드는 독립된 클릭 대상이거나, 독립된 정보 덩어리일 때만 사용한다.
- 상품 카드는 미리보기 → 카테고리/판매자 → 제목 → 가격·평점 순으로 읽힌다.
- 카드 안에 클릭 가능한 자식이 여러 개면, 카드 전체를 링크로 만들지 않는다.
- 모바일에서 카드가 좌우 분할되어 본문이 170px 미만이 될 경우, 시각 영역을 상단으로 올려 세로 구조로 전환한다.
- 장식용 초록 패널 내부의 텍스트는 본문보다 지나치게 작게 만들지 않는다. 390px 기준 최소 0.64rem, 흐름·상태 라벨은 0.76rem 이상을 권장한다.

### 6.4 폼과 상태

- 레이블은 placeholder만으로 대체하지 않는다. 시각 레이블을 숨길 경우에도 `sr-only` 레이블을 둔다.
- 오류는 입력 바로 아래에 원인과 해결 방법을 문장으로 보여 준다.
- 로딩은 위치가 유지되는 Skeleton을 사용한다. 단순히 빈 화면으로 바꾸지 않는다.
- 빈 상태는 “왜 비었는지”와 “다음에 할 수 있는 행동”을 함께 보여 준다.
- 삭제·구매·권한 변경은 처리 중 상태를 표시하고 중복 제출을 막는다.

## 7. 반응형 규칙

### 7.1 기준 폭

| 구간 | 기준 | 설계 원칙 |
| --- | --- | --- |
| 좁은 모바일 | 320~374px | 줄바꿈·터치 영역·가로 넘침을 최우선 확인 |
| 일반 모바일 | 375~480px | 기본 모바일 설계 기준 |
| 태블릿 | 481~768px | 두 열을 쓰기 전에 콘텐츠 폭과 읽기 길이를 확인 |
| 데스크톱 | 769px 이상 | 편집형 좌/우 구성, 넓은 여백 활용 |

### 7.2 반드시 지킬 항목

- 최소 320px, 대표 390px, 데스크톱 1280px에서 화면을 확인한다.
- 가로 스크롤은 마켓 캐러셀처럼 의도된 경우를 제외하고 허용하지 않는다. 페이지 전체의 `scrollWidth`가 viewport보다 커지면 원인을 해결한다.
- `width: 100%` 요소는 padding·border를 고려해 `box-sizing: border-box`를 적용한다.
- 절대 배치 오브제는 정보의 일부가 아니어야 한다. 모바일에서 텍스트와 겹치면 숨기거나 배경으로 약화한다.
- 데스크톱의 고정 폭·고정 높이·음수 margin을 모바일에 그대로 가져가지 않는다.
- 중요 제목에 고정 줄바꿈을 넣었다면 320px, 390px, 768px 각각에서 확인한다.
- 섹션별 배경색이 바뀌어도 경계선·패딩·푸터가 잘려 보이지 않는지 마지막 화면까지 확인한다.

### 7.3 홈 핵심 가치 카드의 모바일 규칙

- 모바일은 `시각 패널(상단) → 텍스트(하단)` 구조를 기본으로 한다.
- 카드 제목은 약 2rem 이상을 유지하고, 설명은 0.9rem 이상을 권장한다.
- 초록 시각 패널은 최소 7.5rem 높이를 확보한다.
- 판매/구매 이동 흐름은 `상품 등록 → 구매 완료`, `판매 수익 ↔ 내 라이브러리`처럼 가로로 읽히는 방향을 유지한다. 점선 장식보다 명확한 화살표와 라벨을 우선한다.

## 8. 모션과 인터랙션

모션은 “무엇이 연결되는지”, “어디로 이동하는지”, “어떤 상태가 바뀌었는지”를 보조하는 역할만 한다.

- 기본 전환 시간: 160~240ms
- 섹션 진입/스크롤 표현: 400~700ms 이내, 한 번의 읽기 흐름을 방해하지 않게 사용
- easing: `ease-out` 또는 부드러운 cubic-bezier를 사용하되, 탄성이 강한 효과는 피한다.
- hover 이동: 보통 `translateY(-1px ~ -4px)` 이내
- 자동 반복 애니메이션은 배경 오브제에만 사용하고, 정보·버튼·가격 자체를 반복적으로 움직이지 않는다.
- `prefers-reduced-motion: reduce`에서는 경로 흐름, 카드 부유, 마키 등 자동 모션을 중지하거나 정적 상태로 제공한다.
- 스크롤 기반 인터랙션은 콘텐츠가 없어지거나 조작 불가능해지는 방식으로 만들지 않는다.

## 9. 접근성 기준

- 모든 이미지에는 의미에 맞는 `alt`를, 장식 SVG에는 `aria-hidden="true"`를 사용한다.
- 키보드 포커스는 항상 보이고, 다크/라이트 표면 모두에서 충분한 대비를 가져야 한다.
- 아이콘 단독 버튼에는 `aria-label`을 제공한다.
- 제목은 문서의 계층을 따라 `h1` → `h2` → `h3` 순서로 사용한다. 크기만을 위해 heading을 건너뛰지 않는다.
- 색 대비는 일반 텍스트 4.5:1 이상을 목표로 한다. 작은 라벨을 연한 배경 위에 둘 때 특히 확인한다.
- 모달, Toast, 오류 메시지는 보조기기 사용자에게 상태 변화가 전달되도록 구현한다.
- 클릭·터치 요소는 44×44px에 가깝게 만들고, 인접한 조작 요소 사이에 충분한 간격을 둔다.

## 10. 성능 규칙

- 기능 설명에 이미지를 써야 한다면 목적이 분명한 이미지만 사용하고, CSS·SVG로 표현 가능한 단순 오브제는 외부 래스터 이미지로 만들지 않는다.
- 첫 화면 밖의 큰 이미지에는 지연 로딩을 고려한다. 단, LCP 이미지에는 적절한 크기와 우선순위를 적용한다.
- 스크롤 이벤트를 직접 반복 처리하지 않는다. 필요하면 `IntersectionObserver`를 사용하고 observer는 효과 후 해제한다.
- 긴 마키·무한 애니메이션은 한 페이지에서 하나 이하로 제한하며 `prefers-reduced-motion` 대안을 제공한다.
- layout을 계속 다시 계산시키는 `top`, `left`, `width`, `height` 애니메이션 대신 가능한 `transform`, `opacity`를 사용한다.
- 페이지별 CSS는 전역 선택자 충돌을 만들지 않도록 페이지 루트 클래스 아래에 작성한다. 복잡한 변경 후에는 불필요하게 누적된 이전 규칙을 정리한다.

## 11. 구현 구조 규칙

- 페이지 전용 시각 조합은 `src/pages/<PageName>/components/`에 둔다.
- 두 곳 이상에서 동일한 역할로 쓰이는 버튼, Empty/Error/Skeleton, Footer 같은 UI는 `src/common/ui/`에 둔다.
- 재사용 컴포넌트는 `className` 확장 가능 여부와 상태 API를 먼저 설계한다. 페이지 복사본을 늘리지 않는다.
- 새로운 UI 파일은 JavaScript(`.js`, `.jsx`)만 사용한다. TypeScript 파일과 문법을 추가하지 않는다.
- 아이콘은 우선 `lucide-react` 또는 기존 SVG 문법을 사용한다. 동일한 의미의 아이콘을 각 페이지에서 다른 모양으로 만들지 않는다.
- `Page` 파일은 화면 조립과 상태 분기만 담당한다. 디자인 전용 복잡한 구조는 페이지 전용 컴포넌트로 분리한다.

## 13. 금지 또는 재검토 대상

- 모바일 본문을 시각 요소에 맞추기 위해 0.75rem 이하로 줄이는 것
- 데스크톱에서만 맞는 고정 `height`와 절대 좌표로 핵심 정보를 배치하는 것
- 한 화면에 서로 다른 카드 반경·그림자 언어를 세 종류 이상 사용하는 것
- 정보 없는 영문 문구, 설명 없는 장식 이미지, 의미 없는 자동 모션
- 실제 제공하지 않는 PG 결제, 송금 정산, 자동 세금 처리를 제공하는 것처럼 표현하는 것
- 페이지 안에서 공통 헤더/푸터를 새로 구현하는 것
- 모바일 화면을 확인하지 않은 채 데스크톱 CSS만으로 완료 처리하는 것

이 문서는 화면을 획일적으로 만들기 위한 제약이 아니라, Assetory의 신뢰감과 읽기 쉬움을 유지하면서도 페이지별 개성을 안전하게 만들기 위한 기준이다. 규칙을 벗어나는 것이 더 나은 사용자 경험을 만드는 경우에는 이유, 적용 범위, 모바일·접근성 검증 결과를 작업 기록에 남긴다.
