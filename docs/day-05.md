## 해결한 문제

- 판매 시작 검증에서 `ProductImage.productId`를 직접 조회해 발생한 `500`을 확인했다. 엔티티 연관관계 경로인 `image.product.id`와 `resource.product.id`를 사용하는 명시적 JPQL로 바꾸고, 판매 시작·공개 노출·판매 중지·비노출을 다시 검증했다.
- 판매자 상품 목록 구현 중 Java import가 클래스 바깥에 배치되어 컴파일이 실패했다. import를 패키지 선언 아래로 옮겨 컴파일을 복구했다.
- 상태 전이 구현 중 `ProductResource` import 누락으로 컴파일이 실패했다. import를 추가하고 재컴파일했다.
- 제한된 실행 환경에서 로컬 MySQL TCP 연결이 차단돼 서버가 기동하지 못했다. 로컬 연결이 허용된 실행 환경에서 DB 연결과 API 검증을 진행했다.
- 백엔드를 중복 실행해 8080 포트 충돌이 발생했다. 기존 서버를 사용하거나 `ASSETORY_SERVER_PORT=8081`로 별도 실행하도록 정리했다.
- Postman Collection이 공개 탐색 환경의 `productId=1`을 우선 사용해 다른 판매자 상품에 요청했다. 4단계 전용 런타임 변수 `sellerProductId`로 분리한 뒤 사용자 Runner 전체 통과를 확인했다.
- 문제별 상세 원인·해결 방법·검증 결과는 `docs/troubleshooting.md`에 기록했다.

## 설계 변경사항

- 기존 로컬 `ProductStatus.SUSPENDED`와 Notion 판매 중지 API의 응답 상태 `STOPPED`가 충돌한다.
- Notion API 설계를 기준으로 상태 값을 `STOPPED`로 정렬했고, 판매 시작·중지 API와 공개 노출 전환으로 검증했다.
- Notion의 이미지·FILE 자료 등록은 `multipart/form-data`를 예시로 들지만, 이번 단계는 사용자 승인 범위에 따라 실제 파일 스토리지 없이 URL 기반 메타데이터만 관리한다.
- 따라서 외부 스토리지·업로드 라이브러리를 추가하지 않고, 이미지와 구매 자료의 URL·이름·유형 메타데이터만 저장하는 요청 형식으로 구현한다.

## 오늘의 회고

- 판매자용 상세 조회는 구매 자료의 이름·유형만 노출하고 실제 URL은 숨겨야 하며, 판매 시작은 기본 정보·대표 이미지·구매 자료가 모두 갖춰진 경우에만 허용해야 한다.
- 연관관계의 ID 조건은 파생 메서드 이름에 의존하지 않고 `entity.relation.id` 경로를 명시해 검증해야 한다.
- Postman에서는 환경 변수와 Collection 변수의 우선순위를 고려해, 단계별 런타임 ID 변수명을 겹치지 않게 구성해야 한다.
