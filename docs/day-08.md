# 8일차 작업일지

## 오늘의 목표

- 상품 소유자와 공동 작업자의 권한을 분리하고, 기존 판매자 상품 관리 API의 소유권 검사를 안전하게 확장한다.

## 구현 및 검증 결과

- `product_collaborators` 엔티티를 추가해 상품·초대받은 회원·`EDITOR` 역할·`PENDING`/`ACCEPTED`/`REJECTED`/`REMOVED` 상태를 관리한다.
- 소유자 초대·목록·제거와 초대받은 회원의 수락·거절 API를 구현했다.
- `SellerProductService`의 상품 상세·수정·이미지·자료·판매 상태 검사를 소유자 또는 수락된 편집자 권한으로 통합했다. 상품 삭제와 공동 작업자 관리는 소유자 전용으로 유지했다.
- 실제 `curl` 검증으로 초대, 목록, 중복·자기 자신 초대 차단, 수락, 편집자의 허용 상품 조회·수정·목록, 편집자의 삭제·공동 작업자 관리 차단, 제3자 접근·응답 차단, 잘못된 상태 전이, 제거 후 즉시 권한 회수, 존재하지 않는 회원·상품, 미인증 접근을 확인했다.
- `./mvnw compile`과 승인된 로컬 MySQL 환경의 `./mvnw test`를 통과했다.

## 설계 보완

- Notion의 8단계에는 공동 작업자 API·DB 컬럼·세부 상태가 없어, 최근 6·7단계와 같이 큰 완료 기준을 유지하며 구현에 필요한 최소 모델을 보완했다.
- 소유자는 상품의 기존 `seller_id`로 유지하고, 공동 작업자는 `EDITOR`만 가진다. 소유권 이전과 별도 역할 승격은 현재 단계 범위 밖이다. 초대 수락이 편집 권한을 부여하는 권한 전환이며, 제거가 즉시 권한을 회수한다.

## 다음 작업

- 9단계 판매 통계·예상 정산의 설계·API·DB 흐름을 확인한 뒤 구현한다.

## 역할·최종 승인 정책 확장 (2026-07-29)

- 사용자 승인으로 공동 작업자 역할을 `MANAGER`, `EDITOR`, `VIEWER`로 확장했다. 역할은 회원 전역 권한이 아니라 상품별 권한이다.
- `EDITOR`의 상품 정보·이미지·자료 변경과 `MANAGER`의 판매 시작·중지는 `product_change_requests`에 `PENDING`으로 저장한다. 소유자가 `APPROVED`할 때 기존 상품 관리 로직으로 실제 반영하고, `REJECTED`에는 반려 사유를 남긴다.
- `MANAGER`는 배정 상품 경로에서 주문 집계, 환불 처리, 문의 응답을 즉시 수행한다. `VIEWER`는 배정 상품의 통계만 조회한다.
- 실제 curl로 편집자의 직접 수정 `403`, 승인 전 미반영, 소유자 승인 후 반영, 관리자의 상품 범위 환불·문의·통계 접근, 편집자의 운영 경로 `403`을 검증했다.
