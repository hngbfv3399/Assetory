# Assetory 하네스 엔지니어링

> 최종 갱신: 2026-07-24
> 적용 범위: 이 저장소에서 Assetory를 구현·검토·테스트하는 모든 코딩 에이전트 작업

## 1. 목적

이 문서는 AI 코딩 에이전트가 기능을 많이 만드는 것보다 **현재 기획에 맞는 변경을, 검증 가능한 방식으로, 작은 단위로** 만들도록 돕는 운영 하네스다.

하네스는 프롬프트 한 번이 아니라 다음을 함께 관리한다.

- 작업에 필요한 맥락과 범위
- 변경하면 안 되는 도메인 규칙
- 구현 절차와 권한 경계
- 테스트·실행·리뷰로 이루어진 피드백 루프
- 실제 작업과 설계 변경을 남기는 문서화 방식

## 2. 출처와 우선순위

에이전트는 아래 순서로 판단한다.

1. 사용자의 현재 요청, 명시적 승인, 안전 제약
2. Notion [개발 관리](https://app.notion.com/p/3a5a6bf2033380148284f369b3b9b384), [API 설계](https://app.notion.com/p/3a5a6bf20333808da59dfb53a1c6254c), [DB 흐름](https://app.notion.com/p/3a5a6bf203338015be48efea5ffd2c64)
3. 저장소의 `AGENTS.md`, 이 문서, 회차별 작업일지
4. 현재 코드와 테스트

기획·ERD·API·화면 설계는 1~2일차에 확정됐다. 에이전트는 이를 다시 설계하거나 확장하지 않는다. 실제 구현에서 충돌·누락을 발견했을 때만 다음을 수행한다.

1. 충돌한 설계와 코드 사실을 제시한다.
2. 영향 범위와 최소 변경안을 설명한다.
3. 사용자 승인 범위 안에서만 변경한다.
4. `docs/day-XX.md`의 `설계 변경사항`에 이유와 결과를 기록한다.

Notion의 작업 상태가 로컬의 검증 결과와 다르더라도, 승인 없이 Notion을 수정하지 않는다.

## 3. 제품 모델과 범위

### 제품 목적

별도 쇼핑몰을 만들기 어려운 개인 창작자와 예비 판매자가 디지털 상품의 등록, 고객 문의, 주문, 매출, 예상 정산을 관리하는 판매자 중심 플랫폼이다.

### 역할

| 역할 | 허용된 중심 기능 |
| --- | --- |
| 비회원 | 공개 상품·카테고리·후기 탐색 |
| 회원/구매자 | 찜, 장바구니, 주문, 구매 자료 이용, 문의, 후기, 환불 요청 |
| 판매자 | 상품·이미지·디지털 자료·판매 상태·판매 주문·통계 관리 |
| 공동 작업자 | 후반 단계에서 소유자/편집자 권한에 따라 공동 상품 관리 |

- 현재 구현은 한 사용자가 `BUYER`와 `SELLER` 역할을 함께 가질 수 있게 한다.
- 공동 작업자 기능과 그에 필요한 스키마는 8단계 범위에서만 설계·구현한다.

### 범위 밖

- 실결제 PG 연동
- 실제 송금·정산 처리
- 배송 상태, 배송지, 배송 도메인
- 현재 단계보다 앞선 상품·주문·결제 기능의 선구현

## 4. 도메인 불변 규칙

아래 규칙은 API와 DB 흐름을 구현할 때 깨지면 안 된다.

### 상품과 공개

- 비회원은 공개 상품만 탐색할 수 있다. 회원 전용 동작은 로그인으로 유도한다.
- 판매자만 본인의 상품·이미지·디지털 자료·판매 상태를 변경할 수 있다.
- 판매 중지 또는 비공개 상품은 새 구매 대상이 될 수 없다.
- 디지털 자료는 `product_resources`로 관리하며, 상품 이미지와 구매 자료를 혼동하지 않는다.

#### `POPULAR` 정렬의 단계별 결정

- **3단계 임시 기준:** 주문·결제 데이터가 없으므로 `reviewCount` 내림차순, 동률이면 `createdAt` 내림차순으로 정렬한다.
- **6단계 확정 예정:** 주문·Mock 결제와 주문 항목이 구현·검증된 뒤, 결제 완료된 주문 항목의 상품별 구매 수량 합계 내림차순으로 전환한다. API의 `sort=POPULAR` 값과 응답 형식은 바꾸지 않는다.
- **7단계 보완:** 환불 완료 시 인기 집계에서 제외할지 여부를 환불 상태 정책과 함께 검증한다. 정책이 확정되면 6단계의 집계 조건에도 반영한다.

`POPULAR` 정렬을 확정할 때 반드시 확인할 요소는 다음과 같다.

1. 결제 성공·취소·실패 상태 중 어떤 주문만 집계할지
2. 주문 항목의 `quantity`를 합산할지, 주문 건수를 셀지
3. 환불 완료 주문 항목을 포함할지 제외할지
4. 동률일 때 사용할 보조 정렬 기준과 페이지 간 순서의 안정성
5. 인기 순위가 권한·판매 상태와 무관하게 판매 중 상품에만 적용되는지
6. 취소·실패·환불·다중 수량 주문을 포함한 자동화 테스트
7. 데이터 증가 후 조회 성능을 측정한 뒤에만 집계 컬럼 또는 통계 테이블을 도입할지

### 장바구니와 주문

- 하나의 장바구니에는 여러 판매자의 상품을 담을 수 있다.
- 결제 시 판매자별로 주문을 분리 생성한다.
- 주문은 하나 이상의 `order_items`를 가지며, 각 주문은 하나의 결제만 가진다.
- 동일 상품의 장바구니 중복과 판매 불가 상품의 구매를 막는다.

### Mock 결제와 디지털 접근권한

- 결제는 Mock으로만 처리하며 외부 PG를 호출하지 않는다.
- 결제 성공 후에만 주문 항목별 `product_access`를 부여한다.
- 다운로드·외부 링크 이용은 구매자 본인과 유효한 접근권한을 반드시 검증한다.
- 환불 완료 시 해당 주문 항목의 접근권한을 회수한다.

### 후기·문의·환불

- 후기는 구매 완료된 주문 항목에만 작성할 수 있고, 주문 항목당 하나만 허용한다.
- **3단계 임시 구현:** 공개 후기 조회만 제공하므로 `Review`는 `orderItemId`를 값으로만 보관한다. 6단계에서 `OrderItem` 도메인이 구현되면 연관관계로 전환하고, 7단계 후기 작성 시 구매 완료 여부와 주문 항목당 한 건 규칙을 검증한다.
- 상품 문의방은 상품·구매자·판매자 조합을 기준으로 생성 또는 재사용한다.
- 환불은 주문 전체가 아니라 주문 항목을 대상으로 처리한다.

### 회원과 인증

- 인증된 API는 액세스 토큰의 사용자 식별뿐 아니라 회원 상태를 확인한다.
- 로그아웃과 회원 탈퇴는 리프레시 토큰을 무효화한다.
- 비밀번호와 원문 리프레시 토큰은 저장·응답·로그에 노출하지 않는다.
- `profile_image_url`과 `user_roles`는 현재 구현에서 API/역할 정책을 반영해 추가된 로컬 설계 보완이다. 향후 ERD와 불일치가 문제 되면 변경 이유를 명시해 동기화한다.

## 6. 구현 규약

### 백엔드

- 패키지 기준점: `backend/src/main/java/com/portfolio/assetory`
- 기능 내부에는 필요에 따라 `controller`, `service`, `repository`, `domain`, `dto`를 둔다.
- Controller는 HTTP 요청 검증과 응답만 담당한다.
- Service는 비즈니스 규칙과 트랜잭션 경계를 담당한다.
- Repository는 DB 접근만 담당한다.
- Domain 엔티티를 API DTO로 직접 반환하지 않는다.
- 공통 응답·예외·웹 설정은 `global` 패키지에 둔다.
- API 응답은 항상 `success`, `data`, `message` 형태를 따른다.

### 프론트엔드

- API 호출은 `frontend/src/api`에 둔다.
- 재사용 UI는 `components`, 페이지 단위 화면은 `pages`, 공통 스타일은 `styles`에 둔다.
- 개발 서버의 `/api` 프록시를 통해 백엔드와 통신한다.
- 화면을 만들기 전에 해당 API의 요청, 응답, 인증 조건을 Notion과 백엔드 구현에서 확인한다.

### 의존성과 설정

- 이미 정한 Java, Spring Boot, React, MySQL, 라이브러리 버전을 우선 유지한다.
- 의존성 추가·업데이트는 필요성, 대안, 기존 코드 영향, 검증 방법을 먼저 설명한 후 진행한다.
- DB URL·계정·비밀번호·JWT 비밀값은 환경변수로만 주입한다.
- `.env`, 실제 비밀번호, 토큰, 개인키는 커밋·응답·로그에 포함하지 않는다.

## 7. 에이전트 실행 루프

### 1) 범위 고정

- 단계 시작 전 `docs/progress.md`와 직전 작업일지를 읽고, 이미 완료·검증한 작업과 남은 TODO를 요약한다.
- 구현에 앞서 그날의 목표, 작업 순서, 완료 기준, 범위 밖 항목을 제시한다.
- 현재 요청이 어느 개발 단계에 속하는지 확인한다.
- 관련 Notion API/DB/화면 설계와 현재 코드를 읽는다.
- 불명확한 설계가 기능 결과를 크게 바꾸면 구현 전에 질문한다. 그렇지 않으면 최소 가정과 함께 진행한다.

### 2) 작은 구현

- 한 번에 하나의 응집된 기능을 구현한다.
- 이미 존재하는 코드와 사용자 변경을 보존한다.
- 오류가 나면 새 기능을 계속 추가하지 않고, 오류의 원인과 영향을 먼저 좁힌다.

### 3) 검증

- 코드 변경에 맞는 가장 좁고 현실적인 검증을 실행한다.
- API는 정상·권한 없음·권한 부족·상태 전이·중복/유효성 오류를 고려한다.
- 실행하지 못한 검증은 통과로 표시하지 않고, 이유와 남은 위험을 보고한다.

### 4) 기록과 피드백

- 설계 변경, 실제 오류, 해결 방법, 확인 결과를 `docs/day-XX.md`에 기록한다.
- 실제 오류는 해결 여부와 관계없이 `docs/troubleshooting.md`에 문제점·원인·해결 방법·검증 결과를 기록한다. 민감 정보는 절대 기록하지 않는다.
- 같은 유형의 실패가 두 번 발생하면 이 문서나 `AGENTS.md`에 재발 방지 규칙을 추가한다.
- 검증한 작업은 `docs/progress.md`에서 완료 처리하고, 남은 단계·TODO·다음 작업을 갱신한다.
- 완료 전 변경 diff를 검토하고, 테스트·린트·빌드 결과를 함께 확인한다.

## 8. 기본 검증 명령

실행 환경과 변경 범위에 맞는 명령만 선택한다. 환경변수가 필요한 서버 실행은 실제 값이 주입된 로컬 터미널에서 한다.

| 대상 | 명령 | 확인 목적 |
| --- | --- | --- |
| 백엔드 컴파일 | `cd backend && ./mvnw compile` | Java 코드와 의존성 컴파일 확인 |
| 백엔드 실행 | `cd backend && bash scripts/run-local.sh` | `.env`를 로드한 Spring Boot·MySQL 연결 확인 |
| 헬스 API | `curl http://localhost:8080/api/v1/health` | 공통 응답과 서버 동작 확인 |
| 인증 흐름 | `cd backend && bash scripts/test-auth-flow.sh` | 가입·로그인·재발급·로그아웃·프로필·탈퇴 확인 |
| 프론트 린트 | `cd frontend && npm run lint` | 정적 규칙 확인 |
| 프론트 빌드 | `cd frontend && npm run build` | 배포 빌드 확인 |
| 프론트 실행 | `cd frontend && npm run dev` | UI와 `/api` 프록시 통신 확인 |

향후 도메인별 테스트가 추가되면 이 표에 명령과 책임 범위를 함께 갱신한다.

## 9. 완료 조건과 보고 형식

작업은 다음이 모두 충족될 때만 완료로 보고한다.

1. 요청 범위의 코드와 문서가 일치한다.
2. 관련 검증이 실제로 실행되어 성공했거나, 미실행 사유가 명확히 기록됐다.
3. API·권한·상태 변화가 도메인 불변 규칙을 깨지 않는다.
4. 민감 정보와 무관한 변경만 Git 대상에 남아 있다.
5. 설계 변경이 있었다면 이유와 영향이 작업일지에 기록됐다.

최종 보고에는 다음만 간결하게 적는다.

- 바뀐 결과와 주요 파일
- 실제 실행한 검증과 결과
- 남은 미검증·위험·다음 작업

## 10. 참고한 최신 가이드

- OpenAI의 [Harness engineering: leveraging Codex in an agent-first world](https://openai.com/index/harness-engineering/)의 원칙을 적용했다. 즉, 짧은 `AGENTS.md`는 지도로 두고, 상세한 지식·계획·기록은 `docs/`에 둔다.
- 최신 Codex 매뉴얼의 `AGENTS.md` 권고를 적용했다. 저장소 구조, 실행·검증 명령, 제약, 완료 조건을 지속 가능한 지침으로 유지한다.
- 이 문서는 외부 가이드를 그대로 복제하지 않고, Assetory의 Notion 기획과 현재 구현에 맞게 범위와 검증 기준을 구체화한 것이다.
