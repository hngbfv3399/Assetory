## 구현 및 검증 결과

- 상품 탐색 화면의 아이보리 바탕, 카테고리 필터, 정렬, 상품 카드를 선명한 테두리와 작은 반경의 편집형 표면으로 통일했다.
- 상품 카드는 페이지 이동 의미에 맞게 `Link`로 변경했고, 미리보기 이미지를 불러오지 못하면 `PREVIEW UNAVAILABLE` 상태를 보여 준다.
- 상품 상세 화면의 과도한 뉴모피즘을 제거하고, 공통 헤더·가격·판매자·Mock 결제 CTA·후기 영역을 같은 테두리 체계로 정리했다.
- 로그인 화면의 큰 뉴모피즘 카드와 입력 그림자를 제거하고, 레이블이 있는 편집형 폼으로 변경했다.
- 320px, 390px, 1280px에서 상품 탐색·상품 상세·로그인 화면을 확인했다. 320px에서 세 화면 모두 페이지 가로 넘침이 없었다.
- `cd frontend && npm run lint`, `cd frontend && npm run build`를 통과했다.

## 추가 작업 — 계층형 카테고리 탐색

- 기존의 평면 카테고리를 상위 분류와 세부 분류로 확장했다. 상위 분류는 디자인·개발·전자책을 유지하고, UI/UX·게임 에셋·아트·일러스트·영상·모션·웹·앱 템플릿·코드·라이브러리·프로그램·도구·판매·운영 가이드·영상 강의·비즈니스 자료를 추가했다.
- `categories.parent_id`를 JPA 로컬 스키마 갱신으로 추가했고, 로컬 시더가 기존 100개 Mock 상품을 세부 분류에 재배치하도록 구성했다. 상품을 삭제하지 않았고, 기본 개발 DB에서 실제 반영했다.
- `GET /api/categories`는 상위 분류와 `children` 목록을 반환한다. `GET /api/products?categoryId=`는 세부 분류뿐 아니라 상위 분류 선택 시 그 하위 상품까지 함께 조회한다.
- 상품 탐색 화면은 상단의 큰 분류 카드와 왼쪽 세부 분류 필터로 구성했다. 390px에서는 가로 스크롤 가능한 세부 분류 영역으로 전환한다.
- 실제 API에서 디자인 상위 분류 48개, UI/UX 세부 분류 10개를 확인했고, 브라우저에서 세부 분류 클릭 시 URL과 상품 수가 함께 변경되는 것을 확인했다.
- `.env`를 로드한 `cd backend && ./mvnw test`에서 애플리케이션 컨텍스트와 판매자 주문 서비스 테스트를 포함한 2건이 모두 통과했다.

## 추가 작업 — 로컬 상품 Mock 데이터

- `local` 프로필에서만 실행되는 `LocalSampleDataInitializer`에 공개 상품 100개를 추가했다. 각 상품은 디자인·개발·전자책 카테고리에 순환 배치되고, 가격·설명·대표 이미지 URL을 가진다.
- 시더는 상품명으로 존재 여부를 확인하므로, 같은 로컬 DB에서 애플리케이션을 다시 시작해도 이미 생성된 100개를 중복 삽입하지 않는다.
- 별도 8081 로컬 서버에서 시더를 실행한 뒤 `GET /api/products?page=0&size=1&sort=LATEST`로 공개 상품 총 110개(기존 10개 + 추가 100개)를 확인했다. 생성에만 사용한 8081 서버는 종료했고, 기존 8080 개발 서버와 DB 데이터는 유지했다.
- `cd backend && ./mvnw compile`을 통과했다.

## 추가 작업 — 상품 탐색·판매 방식 안내

- Gumroad의 넓은 카테고리 탐색과 상품 상세의 판매 정보 구조를 참고하되, Assetory의 편집형 브랜드와 Mock 결제 범위에 맞춰 적용했다.
- 상품 탐색의 카테고리를 설명·행동 문구를 가진 넓은 카드로 바꾸고, 전체·디자인·개발·전자책별로 어떤 자료를 찾을 수 있는지 표시했다.
- 상품 상세에 판매 방식, Mock 결제, 결제 후 내 라이브러리 이용 흐름을 설명하는 안내 영역을 추가했다. 실제 청구·송금이 없다는 제한도 함께 명시했다.
- 1280px와 390px에서 화면을 확인했다. 모바일 카테고리 카드는 콘텐츠 너비를 유지하는 의도된 가로 스크롤이며, 페이지 전체 가로 넘침은 없었다.
- `cd frontend && npm run lint`, `cd frontend && npm run build`를 통과했다.

## 판매자 센터 UI 1차 설계 (2026-08-05)

- Notion의 판매자 상품 관리 계약을 기준으로 `/seller` 판매자 센터 화면을 추가했다.
- 대시보드에는 이번 달 매출·결제 완료 주문·판매 중 상품·처리할 요청과 판매 시작 전 보완할 상품을 표시한다.
- 내 상품 화면은 `DRAFT`·`ON_SALE`·`STOPPED` 상태 탭, 상품 목록, 상태별 안내를 제공한다.
- 새 상품 등록 화면은 기본 정보 입력과 대표 이미지·활성 구매 자료의 판매 시작 조건을 함께 보여 준다.
- 실제 인증과 판매자 API 연결은 로그인 작업과 함께 진행한다. 그 전까지는 화면 검토를 위한 데모 데이터와 비활성 저장 버튼을 사용한다.
- 1280px 브라우저에서 대시보드·내 상품·새 상품 등록 화면 및 전환 URL을 확인했다.
- 판매자 스튜디오 전역 메뉴(Home, Products, Sales, Payouts, Discover)와 Products 하위 메뉴(New product, All products, Affiliated, Collabs)를 추가해 상품 관리 진입점을 우선 배치했다.
- Products는 판매자 Home과 분리된 독립 화면으로 구성하고, 인증·실데이터 연결 전에는 상품 목록 대신 첫 상품 등록을 유도하는 초기 상태 화면을 보여 주도록 조정했다.

## 판매자 스튜디오 화면 설계 반영 (2026-08-05)

- Gumroad의 좌측 앱 네비게이션 구조와 Notion의 판매자·공동 작업자 요구사항을 비교해 `/seller`를 공개 스토어와 분리된 판매자 스튜디오로 재구성했다.
- Home, Products, 새 상품, 상품 상세, Sales, 예상 정산 화면을 같은 앱 셸 안에 배치했다. 판매자 영역에서는 공개 스토어의 공통 헤더·푸터를 표시하지 않는다.
- Products는 전체 상품·내 소유·공동 작업 상품 범위와 상태를 보여 주고, 상품 상세에서는 개요·기본 정보·이미지·구매 자료·공동 작업자·변경 요청·운영 탭을 제공한다.
- 공동 작업자는 상품 단위로 표시한다. 소유자는 승인·초대 권한을, 매니저는 판매·운영 요청 권한을, 편집자는 상품 정보·이미지·구매 자료 변경 요청 권한을, 뷰어는 통계 열람 권한을 가진다는 현재 API 계약을 화면에 반영했다. 변경 요청의 최종 승인·반려 권한은 소유자에게만 둔다.
- Sales에는 주문·문의·환불 운영 진입점과 빈 상태를, 예상 정산에는 결제 완료 매출·환불 차감·플랫폼 수수료(10%)의 계산 구조와 추이·상품별 판매 영역을 배치했다. 실제 송금은 범위 밖임을 명시했다.
- 로그인 및 실제 판매자 API 연결 전 단계이므로, 상품·팀·요청·집계는 화면 검토용 데모 데이터이며 버튼은 데이터를 변경하지 않는다.
- 1280px에서 공동 작업자·판매 운영·예상 정산 화면을, 390px에서 공동 작업자 화면을 확인했다. 모바일은 좌측 메뉴가 상단 가로 목록으로 전환되며, 콘텐츠는 한 열로 표시된다.
- `cd frontend && npm run lint`, `cd frontend && npm run build`를 통과했다.
